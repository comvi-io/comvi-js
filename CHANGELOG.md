## [0.7.1]

Coordinated `0.7.1` release for the main `@comvi/*` package train. Independently versioned packages included below keep their own versions. Detailed package-level notes and migration guidance are available in the linked GitHub Release.

### Patch Changes

- **@comvi/vite-plugin** — A `fileTemplate` without `{namespace}` (`{languageTag}.json`, `{languageTag}/messages.json`) generated keys like `"undefined:hello"`, so the typed keys never matched. Such a template is one catalog per locale: its keys now land in `defaultNs` (default `"default"`), the same as root files under the default template.
- **@comvi/next, @comvi/nuxt, @comvi/react, @comvi/solid, @comvi/svelte, @comvi/vue** — `formatNumber`, `formatDate`, `formatCurrency` and `formatRelativeTime` are now exported from every binding, so code outside a component no longer needs `@comvi/core` as its own dependency. `@comvi/svelte` also exports them from `@comvi/svelte/format`, which imports nothing but `@comvi/core`, for code reached by plain Node (tests, scripts), where the root's `T.svelte` cannot load. `@comvi/next` has them on the root, `/client` and `/server`; `@comvi/nuxt` exports them from `@comvi/nuxt/i18n` and registers them as auto-imports at a low priority, so an app's own `formatDate` and the like keep winning. Each is core's own function, re-exported by name, so an app that does not format pays nothing.
- **@comvi/core, @comvi/react, @comvi/solid, @comvi/svelte, @comvi/vue** — The formatters now pass the fallback-locale chain to `Intl`: without an explicit `locale` argument they format with `[locale, ...fallbackLocales]`, so a locale the runtime has no data for formats in the first fallback it does have instead of the runtime default. A fallback `Intl` rejects as a tag (a catalog key such as `en_US`) is skipped, never thrown on. An explicit `locale` argument is still passed alone. `LocaleSource` gains an optional `fallbackLocales`, and the instance exposes `i18n.fallbackLocales`, a read-only array that `setFallbackLocale()` replaces rather than changes. The bound formatters in every binding follow the same chain and re-render on `setFallbackLocale()`; `useFormatters()` identity is now stable per locale and fallback chain.
- **@comvi/cli** — `comvi translate` and `comvi pull` wrote every catalog with two-space indentation, LF and a final newline, so a repository formatted with tabs, four spaces or CRLF failed its formatter check after each run. Both now write a file in its own indentation, line endings and final newline. A new file takes those of the source locale's file for the same namespace (`pull` uses `sourceLocale` from `.comvirc.json`), else two spaces and LF as before.
- **@comvi/core** — The format helpers no longer rebuild an I18n instance's fallback-locale chain on every call.
- **All packages** — Development and build dependencies were updated to close security advisories in the build and test toolchain. Runtime and peer dependency ranges, the API and the type declarations are unchanged.
- **All packages** — Built and tested with updated development tooling (Vitest 5, vite-plugin-dts 5, Prettier 3.9, Tailwind CSS 4.3, @types/react 19.3). No runtime, API or dependency-range changes. The `I18nProvider` and `ComviClientProvider` declarations spell their return type `import('react').JSX.Element` (the same type), and the in-context editor's stylesheet is regenerated by Tailwind CSS 4.3.
- **@comvi/plugin-in-context-editor** — The editor's interface is now built with reka-ui 2.11, @lucide/vue 1.61 and tailwind-merge 3.7. They are bundled into the editor's files as before, so there is nothing new to install, and the editor's API and options are unchanged.

## [0.7.0]

Coordinated `0.7.0` release for the main `@comvi/*` package train. Independently versioned packages included below keep their own versions. Detailed package-level notes and migration guidance are available in the linked GitHub Release.

### Minor Changes

- **@comvi/cli** — **Breaking: one exit-code scheme for every command.** CI can now tell a conflict, an outage and a bad key apart
- **@comvi/cli** — `comvi check`: offline validation of local catalogs against the source locale (missing, stale, empty source, parameters, plural, select, tags, unsupported ICU, and opt-in identical); text and JSON output. Exit codes follow the CLI's scheme: 0 clean, 1 findings (or a local failure that fits no other code), 4 invalid input (flags, config, a catalog or directory it cannot read, an unknown locale, a usage error); `check` never talks to the platform, so never 2 or 3. No API key, `.comvirc.json`, `.env` or network needed. A `.comvirc.json` read by `check` may use a `fileTemplate` without `{namespace}` (`{languageTag}.json`); `pull` and `push` still require it.
- **@comvi/cli** — New command `comvi translate`. It machine-translates the values your project is missing on the platform and writes them into your local files. The translations are saved on the platform as not reviewed.

### Patch Changes

- **@comvi/cli** — `comvi push --force-mode ask` no longer overwrites a value saved on the platform after its preview. When the preview finds no conflict, the push now commits with conflict checking on (`fail`) instead of `override`. A value a translator saves between the preview and the commit then stops the push. The error says how many values changed, that nothing was written, and to run the push again. The platform side of this check, which compares under its lock, ships with the matching platform release.
- **@comvi/cli** — `comvi push` gives the commit request five minutes instead of 30 seconds, so the first push of a large catalog no longer reports a timeout for a push the platform then applies. A commit that does time out now says the push may already have been applied and that re-running it is safe.
- **@comvi/cli** — `comvi pull --empty-dir` no longer deletes everything under the translations directory.
- **@comvi/cli** — `comvi pull` shows what it changes in each file
- **@comvi/cli** — `comvi push` reports what the platform actually did. Before, "Updated" counted the conflicts kept on the platform in `keep` mode and was 0 after a real overwrite.
- **@comvi/cli** — Smaller CLI fixes
- **@comvi/cli** — `comvi typegen --watch` survives a platform deploy and stops loudly when it cannot recover.
- **@comvi/cli** — `ConfigLoader.load` accepts `{ requireApiKey, optional }`: with `requireApiKey: false` it neither requires an API key nor reads `COMVI_API_KEY` / `COMVI_API_BASE_URL`, and with `optional: true` a project without `.comvirc.json` loads the defaults. `.comvirc.json` accepts `sourceLocale` and a `check` section (`identical`, `strict`).
- **@comvi/vite-plugin** — Internal: the ICU scanner that reads parameters out of translation values moved to the workspace-private typegen module, so other tools can share it. Generated types are unchanged for every message `@comvi/core` accepts. One change for messages core refuses: a `plural` or `selectordinal` explicit value outside core's grammar (`=x`, `=1e3`, `=.5`, `=+1`, `=Infinity`) now makes the key report the ICU issue and get no parameters, as `{price, number}` already did, instead of generating parameters for a key core rejects with `E_ICU_SYNTAX`.
- **@comvi/plugin-in-context-editor** — Saving in the in-context editor now writes only the languages whose value changed. Before, every language of the key was sent back and marked "not reviewed" on the platform, so one German edit also reset the review status of the untouched English and French values. A value typed back to what was stored, or one a plural or variant switch leaves as it was, is not sent either.
- **@comvi/plugin-in-context-editor** — A save in the in-context editor with nothing to write no longer sends a request. Before, an edit typed and then reverted still sent the key's plural flag, which could undo a plural change a teammate had just made on the platform. A save the platform accepted now also stays saved when the page cannot show the new value at once (for example a message the runtime rejects in development): the editor reports that the value appears after a reload, and saving again sends nothing.
- **@comvi/nuxt** — The package description on npm now says what the module does (type-checked keys, ICU plurals, a `<T>` component for markup inside translations) instead of naming Nuxt versions.

## [0.6.0]

Coordinated `0.6.0` release for the main `@comvi/*` package train. Independently versioned packages included below keep their own versions. Detailed package-level notes and migration guidance are available in the linked GitHub Release.

### Minor Changes

- **@comvi/core** — Keep flat plain-object catalogs by reference instead of copying them. A catalog passed to `messages`, `addMessages()` or returned by a loader is eligible when every leaf is a string and its prototype is either null or exactly `Object.prototype` — the latter only while `Object.prototype` itself carries no enumerable key. It is validated with one pass over its enumerable keys and then stored as the object you passed. Everything else (a nested value, a non-string leaf, any other prototype, or a polluted `Object.prototype`) is still flattened into a fresh null-prototype copy.
- **@comvi/core** — `#` inside `plural` and `selectordinal` is now formatted for the message's locale, as ICU MessageFormat defines it: `{count, plural, other {# items}}` renders `1,234 items` in `en` and `1.234 items` in `de`. Previously `#` inserted the raw digits. `#` follows the `Intl.NumberFormat` defaults, so a fractional count is rounded to three fraction digits (`1.23456` renders `1.235`). Exact-match selectors (`=0`, `=1`) still compare the number itself. A count of negative zero renders `0`, without a sign. Use `{count}` instead of `#` where the raw digits are wanted.
- **@comvi/next** — **Behaviour change: `createNextI18n` no longer composes browser-extension discovery.** Until now it attached discovery to every Next app on its own, so the i18n instance was published on `window.__COMVI__` and got an auto-generated `instanceId`. Now a Next app is not visible to the Comvi browser extension, and `i18n.instanceId` is `undefined`, until the app composes discovery itself, as with every other binding.

### Patch Changes

- **@comvi/core** — Reduce template-cache lookup overhead: compiled templates are now partitioned by a numeric key (message compiler, syntax extensions, plural `#` context) instead of a string built on every lookup, still bounded by one global 1000-entry FIFO.
- **@comvi/core** — `devtools()` installs a page-level editor loader the Comvi browser extension uses to load the in-context editor from jsDelivr; new `editorVersion` option pins the editor. The `EditorLoadResult` type declares `editorVersion`, `code` and `host` as always present, holding `undefined` where they do not apply.
- **@comvi/core** — `devtools({ editorVersion })` fails closed. An explicit value that is not an exact version (SemVer `major.minor.patch` with no leading zeros, optionally with a prerelease such as `0.6.0-rc.1`; build metadata is not accepted) no longer falls back to `latest`: the editor loader is still installed so the Comvi browser extension can explain the problem, but it requests nothing, and its `load()` answers the new failure code `invalid-editor-version`. The extension's popup tells the translator that the pin must be an exact version like `1.2.3`, and development builds warn as before. Leaving `editorVersion` out, or passing `"latest"`, still loads `latest`.
- **@comvi/plugin-in-context-editor** — The in-context editor counts its stylesheet as adopted wherever it sits among the shadow root's adopted sheets, and takes a half-finished adoption back before it falls back to a `<style>` element, so its styles are never applied twice.
- **@comvi/plugin-in-context-editor** — In the in-context editor, translation text no longer jumps to the right when you start editing a field, and the source language is now listed first with a neutral `Source` marker instead of an orange tint.
- **@comvi/plugin-in-context-editor** — The in-context editor now applies its styles through a constructable stylesheet instead of an inline `<style>` element, so it renders on sites whose Content Security Policy has a strict `style-src`; the standalone build also exposes its own `version` and reports the `devtools()` editor loader it found in `getStatus().hook`.
- **@comvi/plugin-in-context-editor** — The "Languages" picker in the in-context editor now shows all of its languages instead of letting the first translation field draw over them.
- **@comvi/core** — A `{name}` placeholder whose parameter is a function no longer prints the function's source code. It now renders as a missing parameter does: the literal `{name}` by default, with a development warning that says the parameter is a function, or an empty string under `missingParam: "drop"`. This is what a translator hits by typing `{link}` where the message needs `<link>…</link>`, both in `t()` with a tag handler and in `<T components={{ link }}>`. Tag handlers themselves, and every other parameter value, are unchanged.
- **@comvi/core** — In development, the "parameter is a function" warning and the "missing parameter" warning no longer silence each other for the same message and placeholder, and the warning always describes the value that was rendered.
- **@comvi/core** — `#` in a plural branch resolves to that plural's count even after a tag handler inside the branch calls `t()` and catches what that render throws. Until now the count the failed inner plural had set stayed behind, and the outer `#` printed it.
- **@comvi/core** — `icuCompiler` no longer reads an argument whose only comma sits inside a nested pair of braces as a parameter. `{{,}\t}` used to become a parameter named `{,}`, and `{{count, plural, …}}` a parameter named after the whole inner plural. Such an argument now fails like any unsupported ICU syntax, as the default compiler already did: `E_ICU_SYNTAX` at ingestion in development, and in production the braced text renders literally and is reported once through `onError`.
- **@comvi/next** — The `<I18nProvider>` JSDoc example names the hand-written `"use client"` wrapper of the manual setup `ClientProvider`, and says that `<ComviProvider>` from `@comvi/next/server` makes it unnecessary under `withComvi`.
- **@comvi/next** — Add `@comvi/next/proxy` for Next.js 16's `proxy.ts` file convention. Next 16 renamed `middleware.ts` to `proxy.ts` with the same request handler, so `@comvi/next/proxy` exports the same `createMiddleware` as `@comvi/next/middleware`: write `export default createMiddleware(routing)` in `src/proxy.ts` on Next 16. `@comvi/next/middleware` stays for Next 15's `middleware.ts`, and both subpaths hand out one function. Next 16 runs `proxy.ts` on the Node.js runtime and rejects a `runtime` option there; `createMiddleware` runs on either runtime.
- **@comvi/nuxt** — Check `localeDetection.resolveAcceptLanguage` at build time with `vm.Script` instead of `new Function`, so the module no longer uses `new Function`. The source is compiled to check that it parses and is never executed.
- **@comvi/cli, @comvi/vite-plugin** — Generated types accept a number for a bare `{name}` and for a `select` variable: such a parameter is now `string | number`, not `string`. `t("errors.count", { count: 3 })` against `"Reported misses: {count}"` no longer fails `tsc`; the runtime always rendered it. A `plural` or `selectordinal` count stays `number`. `comvi typegen` and `comviTypes()` still write byte-identical files, so a file with such a parameter has to be regenerated once after upgrading, or `comvi typegen --check` reports it as stale.

## [0.5.0]

Coordinated `0.5.0` release for the main `@comvi/*` package train. Independently versioned packages included below keep their own versions. Detailed package-level notes and migration guidance are available in the linked GitHub Release.

### Minor Changes

- **@comvi/cli** — `comvi typegen --check` now has distinguishable exit codes, and `comvi init` refuses a malformed `--api-url` instead of writing it.
- **@comvi/cli** — **Config discovery stops at your project, instead of walking to the filesystem root.** `comvi` climbed from the working directory all the way up looking for `.comvirc.json`, so a stray one in `$HOME` or in a shared CI working directory was adopted, with whatever `apiKey` it carried.
- **@comvi/cli** — **Breaking:** `--env-file <path>` is now `--dotenv <path>`, and `--no-env-file` is now `--no-dotenv`. `COMVI_NO_ENV=1` is unchanged.
- **@comvi/cli** — `comvi push` now exits with code 4 when the force mode is invalid, whether it came from `--force-mode` or from `push.forceMode` in `.comvirc.json`. It used to exit 1, which is the generic-failure code, while every other validation failure — an unparseable config, an unknown namespace — already exited 4. Scripts that branch on the exit code can now treat 4 as "you gave me bad input" for this case too; anything still checking for 1 here needs updating.
- **@comvi/cli** — `comvi init` no longer destroys an existing `.comvirc.json`, and its next-steps list is numbered correctly.
- **@comvi/cli** — **BREAKING (breaking change on a 0.x minor): type generation has one command name, `comvi typegen`.** The `generate-types` and `generate` spellings are removed; `comvi init` prints `comvi typegen` in its next steps.
- **@comvi/cli** — `comvi push` now flattens nested JSON to dotted keys instead of uploading `[object Object]`.
- **@comvi/cli** — Type generation now runs on one shared emitter, the same one `@comvi/vite-plugin` uses, so the two tools cannot drift. The emitter is workspace-private and is bundled into this package — **no new dependency, nothing extra to install**, and the published types still declare `SchemaParam`, `KeySchema` and `ProjectSchema` themselves.
- **@comvi/core** — `@comvi/core/loader` now exports `acquireLoaderApi(instance)` and `@comvi/core/plugins` exports `acquirePluginsApi(instance)`: given an i18n instance, each returns the component-driveable slice of its capability — the loader's namespace-activation and reload members, the plugins capability's `onMissingKey` — or throws `missingCapability(...)` when the capability was never composed on, in development and in production alike. The returned bag is cached per instance, so two callers holding the same instance get the same function references.
- **@comvi/core, @comvi/react, @comvi/solid, @comvi/svelte** — `AnyI18nInstance` — the instance type a provider accepts, whatever `defaultParams` type it carries, with the `strictFunctionTypes` invariance write-up — is declared once in `@comvi/core` and re-exported as a type by `@comvi/react`, `@comvi/solid` and `@comvi/svelte`, instead of three identical copies. No shape change; `scripts/wrapper-hooks-parity.test.mjs` now fails on a local re-declaration.
- **@comvi/core** — `@comvi/core` is compiled with `useDefineForClassFields: false` — a smaller bundle on every entry, with no logic change.
- **@comvi/core** — **BREAKING (breaking change on a 0.x minor): `clearMessages(undefined, ns)` no longer deactivates the namespace.** Every form of `clearMessages(locale?, namespace?)` now clears CONTENT only. Deactivation is the new `removeActiveNamespace(ns)` on the loader capability.
- **@comvi/core, @comvi/plugin-in-context-editor, @comvi/react, @comvi/solid, @comvi/svelte, @comvi/vue** — **BREAKING (breaking change on a 0.x minor): the per-call `raw` option is renamed `markers`, with the polarity inverted.** `t('meta.title', { raw: true })` becomes `t('meta.title', { markers: false })`. Core never read the option; its one reader is the in-context editor, which appends invisible marker characters to every result so it can find the text on the page. `markers: false` turns those characters off for this call, for when they cause a problem: a comparison or sort that sees extra characters, a width-sensitive layout, a canvas or library that counts characters. The new name says exactly that; nothing else reads it, and the string is then not editable in context. Leaving it out, or passing `true`, keeps the markers as before. `markers` stays a reserved call-control key: it is not an interpolation value, and `defaultParams` rejects it beside `locale`, `ns`, `fallback` and `tagInterpolation`.
- **@comvi/core** — Core enablers for framework bindings running on the base `@comvi/core` instance.
- **@comvi/core** — **`window.__COMVI__` discovery protocol v2.** The v1 registry object (`version` / `instances` / `register` / `unregister` / `get`, plus the `COMVI_READY` event) is gone, and announcing is a capability now rather than a constructor behaviour.
- **@comvi/core** — Three tree-shakeable additions to `@comvi/core`, free for non-importers
- **@comvi/core** — ICU arguments the compiler does not implement now fail the same way ICU syntax already failed on the default compiler: development throws at ingestion, production renders the text literally and reports `E_ICU_SYNTAX`. The ICU compiler supports `plural`, `selectordinal` and `select` — those three only.
- **@comvi/core, @comvi/plugin-fetch-loader** — **A loader now fetches the fallback chain, and an empty translation falls through to it.**
- **@comvi/core** — **`loader(importMap)` now REQUIRES the import map, so `attachLoader` is the one attach-only loader installer.** One capability had three installers and a decision rule keyed on bundle bytes the reader could not see: `loader` names the import-map adapter statically, so a bare `loader()` was attach-only and still pulled ~111–124 B min+gz of adapter into the graph, and the docs told you to weigh that against typing `attachLoader`. The rule is now one sentence
- **@comvi/core** — The catalog cache follows the `messages` naming: the `TranslationCache` class and type are `MessagesCache`, and the instance getter `translationCache` is `messagesCache`. The old names are removed.
- **@comvi/core** — Inline catalogs are now passed as `createI18n({ messages })`, and the catalog methods are `addMessages()`, `getMessages()`, `clearMessages()` and `reloadMessages()`; the `translationsCleared` event is `messagesCleared` and the `FlattenedTranslations` type is `FlattenedMessages`. The old names are removed, and a non-object `messages` throws `E_MESSAGES_NOT_OBJECT`.
- **@comvi/core** — `MessagesMap` is exported from `@comvi/core` and types `addMessages()` and the `messages` option; messages and JSDoc say "i18n instance" instead of "host", and the never-emitted `configChanged` source `"messagesAdded"` is removed.
- **@comvi/core** — Missing interpolation parameters now render as the literal placeholder instead of silently disappearing, governed by the new `missingParam` option (default `"literal"`).
- **@comvi/core, @comvi/react, @comvi/solid, @comvi/svelte, @comvi/vue** — **Security: a translation param that only looks like a node is rendered as text.** Core decided whether a param was a virtual node from its shape, and every `<T>` then rendered it as an element with its own tag and props. A plain object of that shape, such as a value from an API response or a URL passed as `name`, became a real element chosen by whoever sent the data.
- **@comvi/core** — New `prepareTranslation(i18n, props)` — the shared `<T>` pipeline, on the pure `@comvi/core/rich-text` seam. It absorbs the plumbing the vue / react / solid / svelte wrappers each used to duplicate: marker-based handler transport, `childrenToArray`, reserved-prop forwarding (`ns` / `locale` / `fallback` / `markers` override same-named `params` keys only when defined) and the missing-translation check. It passes the tag syntax extension **per call**, so `<T>` rendering never depends on ambient registration or import order. `@comvi/core/tags` re-exports it unchanged beside that registration, and every framework `<T>` imports the pure seam.
- **@comvi/core** — `setLocaleAsync()` is renamed to `setLocale()`, which returns a promise that settles once the locale applies; with a loader composed, it first loads the active namespaces. The old name is gone, and assigning `i18n.locale` remains the switch that does not wait.
- **@comvi/core** — **BREAKING (breaking change on a 0.x minor): the root `@comvi/core` entry changes semantics.** `@comvi/core` is now ONE entry — the base instance — and capability is an import you add, never an entry you switch. The second entry, `@comvi/core/slim`, is deleted; it never published, so there is no deprecation debt.
- **@comvi/core** — New subpath entries decompose the core, so an app pays only for what it composes
- **@comvi/core** — Two more capabilities moved out of the base core into subpaths that compose them back.
- **@comvi/core** — **Added: `.use(installer)` — the composition pipe — plus the configured capability installers `loader()`, `plugins()` and `devtools()`.** Composing a capability used to wrap the construction expression; now it continues it.
- **@comvi/core** — `i18n.withMessages(catalogs)` returns a read view whose `t`, `tRaw` and `hasTranslation` read each key from the given `"locale:namespace"` catalogs first and from the cache otherwise, without writing the i18n instance.
- **@comvi/core, @comvi/nuxt, @comvi/plugin-in-context-editor** — New `@comvi/core/editor-bridge` subpath: the typed contract for the in-context editor mappings bridge, previously hand-copied in two places. It exports `EDITOR_MAPPINGS_GLOBAL` / `EDITOR_INITIAL_MAPPINGS_GLOBAL` (the property keys on the instance), the `InContextEditorMappings` interface, the `toRecordOfNumbers()` payload validator and the `readEditorMappings(instance)` guard. The module is pure and invisible to non-importers.
- **@comvi/plugin-in-context-editor** — The standalone runtime speaks discovery protocol v2. On boot, and again on `activate()`, it drain-and-swaps `window.__COMVI__`: it snapshots the queue array, swaps in a dual-protocol hook object first, then drains the snapshot. The hook implements both protocols — v2 `push` / `remove` for new core, and the v1 surface (`register` / `unregister` / `get` / `instances`) so an OLD `@comvi/core` landing on a page where the new editor already swapped still attaches. A pre-existing v1 registry object is drained via its `instances` map, and a truthy non-conforming global is left untouched. `getStatus()` reports version and instance counts from whichever shape currently occupies the global.
- **@comvi/plugin-in-context-editor** — **BREAKING (breaking change on a 0.x minor): the raw plugin factory is renamed `InContextEditorPlugin` → `inContextEditorPlugin`.** This package already spelled the suffix; what it did not do is match the casing of its three siblings, so the four first-party factories now read the same way — `inContextEditorPlugin` beside the `inContextEditor` installer, as `fetchLoaderPlugin` sits beside `fetchLoader`.
- **@comvi/plugin-in-context-editor** — The standalone activation option that refetches catalogs from the Comvi API before click-to-edit is now `refreshMessages`. The old `refreshTranslations` name is removed.
- **@comvi/plugin-fetch-loader** — **BREAKING (breaking change on a 0.x minor): the API host option is `baseUrl`, and only `baseUrl`.** `apiBaseUrl` is removed from `FetchLoaderOptions`, so passing it is a type error. Precedence: `baseUrl` > build-time env overrides (`VITE_API_BASE_URL` / `NEXT_PUBLIC_COMVI_API_URL`) > the new `comviPreset` export, which carries the vendor defaults (`https://api.comvi.io` / `https://cdn.comvi.io`). Internally, the 948-line `src/index.ts` is split into `options` / `http` / `cache` / `loader` modules with an unchanged public surface.
- **@comvi/plugin-fetch-loader** — `cdnLoader` is the package root; `fetchLoader` and the HTTP helpers moved from the root to `@comvi/plugin-fetch-loader/api`.
- **@comvi/plugin-fetch-loader** — Loads land through `addMessages()`, and the late-compose diagnostic now recommends `reloadMessages()`, matching the renamed `@comvi/core` catalog methods.
- **@comvi/plugin-fetch-loader** — **`CDN_BASE_URL` is not exported.** Nothing in the package read it: `cdnUrl` is a required option with no default and no environment override, so the constant and its `VITE_CDN_BASE_URL` / `NEXT_PUBLIC_COMVI_CDN_URL` reads answered a question the loader never asks. `API_BASE_URL` stays, since the API path really does fall back to it, and the hosted CDN default is readable as `comviPreset.cdnBaseUrl`.
- **@comvi/plugin-fetch-loader** — **The project-info request is retried, within bounds.** A 429, a 5xx or a transport failure on `/v1/project` now gets up to two more attempts instead of failing the whole load on one bad moment.
- **@comvi/core, @comvi/next, @comvi/react, @comvi/solid, @comvi/svelte, @comvi/vue** — A nested inline catalog now works on every instance, and `flattenCatalog` stops being an escape hatch.
- **@comvi/core, @comvi/next, @comvi/react, @comvi/solid, @comvi/svelte, @comvi/vue** — ICU is enabled ONLY through the constructor option `compiler: icuCompiler`

## [0.1.0] - 2025-01-30

### Initial Release

A lightweight, type-safe internationalization library with framework-agnostic core and bindings for Vue, React, Svelte, SolidJS, Next.js, and Nuxt.

### Core Features

#### Multi-Framework Support

- **@comvi/core** - Framework-agnostic core package (25.08 kB, 8.07 kB gzipped)
- **@comvi/vue** - Vue 3 bindings with full reactivity support
- **@comvi/react** - React 18+ bindings with hooks
- **@comvi/solid** - SolidJS bindings with reactive primitives
- **@comvi/svelte** - Svelte 4/5 bindings with stores
- **@comvi/next** - Next.js 14+ App Router integration with SSR
- **@comvi/nuxt** - Nuxt 3 module with auto-imports

#### Plugin System

- Extensible architecture with plugin support
- **@comvi/plugin-fetch-loader** - HTTP translation loading with timeout, fallback, and request deduplication
- **@comvi/plugin-locale-detector** - Auto-detect user locale (browser, localStorage, cookies)
- **@comvi/plugin-in-context-editor** - Visual inline translation editing
- **@comvi/cli** - CLI for type generation and translation sync

#### Translation Features

- Nested translations with dot notation (e.g., `welcome.message`)
- Parameter interpolation: `"Hello, {name}!"`
- ICU MessageFormat pluralization: `{count, plural, one {# item} other {# items}}`
- Namespace organization for code-splitting
- Fallback language chains
- Post-processor support for custom transformations
- Missing key and load error callbacks

#### Developer Experience

- TypeScript-first with full type safety
- Reactive state management per framework
- Progressive loading pattern (show UI immediately, load translations in background)
- Guaranteed-ready pattern (await translations before app start)
