**One name for the SSR render locale: `ssrLocale`.** `@comvi/solid` had no way to seed one, though it has `renderToString` and hydration, so a server render could only ever paint the host's configured locale and the hydrating client silently disagreed with it until the first reactive update repainted. `<I18nProvider ssrLocale="fr">` now adopts that locale onto the host during the render phase, before the locale signal is seeded — the same contract `@comvi/vue`'s option of that name has, and the reason `t()` and `locale()` cannot drift apart. Adopting it is a WRITE to `i18n.locale`, so a solid app that server-renders must build its host inside the request handler: a module-scope host shared by every concurrent request would carry one request's locale into another's tree. The package README's SSR section shows the per-request shape. `@comvi/react` accepts `ssrLocale` as well, alongside its original `ssrInitialLocale`. **`ssrInitialLocale` is now `@deprecated`, removed in 0.6** — `ssrLocale` is the canonical, cross-binding name; **`ssrLocale` wins when both are passed** and a development build warns that it did. That is a change from the 0.5 pre-releases, where the deprecated alias won: a reader who fixed the deprecation warning by adding `ssrLocale` beside the old prop got the warning they were chasing and no change to the locale the server painted. React's `ssrInitialIsLoading` / `ssrInitialIsInitializing` are deliberately not ported — they exist for `useSyncExternalStore`'s server snapshot and are correctly react-only. `@comvi/next`'s own client provider now passes `ssrLocale` internally (it used to pass the deprecated `ssrInitialLocale`) and still omits both spellings from its own provider props, since it sets the render locale from its own `locale` prop and either one passed there would be silently overridden.
