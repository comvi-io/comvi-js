**Development build: the dev-only diagnostic now actually fires under a bundler's development condition.** The readable half of the `E_USE_HOST_IDENTITY` error `createNextI18n(…).use` throws — the one that names `.use(definePlugin(f))` / `.use(nextPlugin(f, { runtime }))` and the lowercase-factory rule — was dead code in the published package, so every consumer got the bare `"E_USE_HOST_IDENTITY"` string instead, development included. `__DEV__` is a build-time define of OUR build, `vite build` pins `NODE_ENV=production`, and the package published exactly ONE artifact family, so the only files a consumer could resolve had `__DEV__: false` baked in no matter what mode the app built in.

The package now publishes a second family — `dist/*.dev.js`, one file per module because `preserveModules` is what makes `"use client"` a per-file directive — and EVERY runtime entry (`.`, `./server`, `./client`, `./middleware`, `./routing`, `./navigation`) answers the `"development"` condition with its `.dev` counterpart, the pattern `@comvi/core` and the four bindings use. `"use client"` lands on the same five modules in both families (`client`, `client/I18nProvider`, `navigation`, `routing/Link`, `routing/hooks`), so a Next dev build gets the same client/server split it always had. Every production file is byte-for-byte what it was — no row of the size gate moved — and `types` is unchanged and shared by both families. The claim is gated on the DIST from now on: the bundler-matrix `next-dev-conditions` case bundles a consumer that defines nothing, once per mode per bundler, triggers the error for real, and asserts the readable text is in the development bundle and out of the production one.
