# Migration guide — `@comvi/react` + `@comvi/next` v0.2 → v0.3

This release modernizes the React surface, removes the render-time `i18n.locale` mutation in the Next provider, and adds finer-grained subscription hooks. See ADRs `docs/adr/0001`..`0004` for the architectural decisions.

If you cannot upgrade today, the **v0.2.x patch line is still supported** and ships the 5 non-breaking fixes from Wave 1.

---

## Breaking changes — what you need to do

### 1. Peer dependency bump — drops React 16.8-17 support

`@comvi/react@0.3.x` now declares `"react": "^18.0.0 || ^19.0.0"`.

- If your app is on React 17 or earlier: stay on `@comvi/react@0.2.x` and `@comvi/next@0.2.x` (Wave 1 fixes available). v0.3 will not install.
- If your app is on React 18+: no action required. The `use-sync-external-store` shim has been removed in favor of the native `useSyncExternalStore`. Bundle size drops marginally.

### 2. `useI18nContext()` is now deprecated (still works through v0.3)

```tsx
// ⚠️ Deprecated in v0.3, scheduled removal in v0.4
const { i18n, locale, translationCache, isLoading } = useI18nContext();

// ✅ Preferred — same fields, sharper subscriptions
const { i18n, locale, translationCache, isLoading } = useI18n();
```

`useI18nContext()` re-renders on every reactive axis (locale, cache, loading) — same behavior as v0.2. `useI18n()` is a drop-in replacement with the same return shape but a finer-grained internal subscription pattern.

### 3. `t` and `tRaw` identity now CHANGES on locale flip (intentional)

In v0.2, `t` and `tRaw` were memoized on `[i18n, ns]` — identity stayed stable across locale changes. This was a hidden tearing surface: the bound function read `i18n.locale` at call time, which could leak the wrong locale during `startTransition`-wrapped locale switches.

In v0.3, `t` / `tRaw` are memoized on `[i18n, ns, locale]` and inject the React-tracked locale into every call. **Identity intentionally churns when locale changes.**

Most code is unaffected — `<T>` and direct `t(...)` calls continue to work. The only impact is for code that put `t` in a `useEffect` deps array:

```tsx
// ⚠️ In v0.3: effect re-runs on locale change (this is the fix)
const { t } = useI18n();
useEffect(() => {
  cache.set("hello", t("hello"));
}, [t]);
```

If this is what you want (re-translate on locale change), no change needed. If your effect was meant to run once on mount, depend on the trigger you actually care about (e.g., the data you're caching).

### 4. `next/client/I18nProvider` internal render-mutation removed

The Next provider used to mutate `i18n.locale = locale` and call `i18n.addTranslations(messages)` during its render body. v0.3 moves both into a `useState(() => ...)` lazy initializer that runs once per component instance, before the first commit.

No API change — `<I18nProvider i18n={...} locale={...} messages={...}>` works identically from the consumer's perspective. The internal change closes Dim 3 P1 in the audit and unblocks future refactors (e.g., concurrent-rendering safety).

## Additive features — new selector hooks

### `useLocale()` — narrow locale subscription

For components that only need the current locale (e.g., `<Link>`, URL helpers, locale-aware buttons), `useLocale()` subscribes ONLY to the locale axis. It skips re-renders on namespace loads and loading-state changes.

```tsx
import { useLocale } from "@comvi/react";

function FlagIcon() {
  const locale = useLocale();
  return <img src={`/flags/${locale}.svg`} alt={locale} />;
}
```

The internal `<Link>`, `usePathname()`, and `useLocalizedRouter()` in `@comvi/next` already use this hook — non-translation routing consumers no longer re-render on every namespace load (audit Dim 4 P1, measurement-confirmed).

### `useIsLoading()` — loading-state slice

For loading UI surfaces that don't need the rest of the i18n bag:

```tsx
import { useIsLoading } from "@comvi/react";

function LoadingIndicator() {
  const { isLoading, isInitializing } = useIsLoading();
  if (!isLoading && !isInitializing) return null;
  return <div className="spinner" />;
}
```

### Core: formatters accept optional `locale` arg

`@comvi/core@0.3.0` adds an optional `locale` parameter to all four format helpers:

```ts
i18n.formatNumber(1234.5, { maximumFractionDigits: 2 }, "de"); // -> "1.234,5"
i18n.formatDate(new Date(), { dateStyle: "long" }, "fr"); // -> "1 mai 2026"
i18n.formatCurrency(99, "USD", undefined, "ja"); // -> "$99.00"
i18n.formatRelativeTime(-1, "day", undefined, "uk"); // -> "вчора"
```

Existing call sites without the argument continue to work — the helpers fall back to the instance locale. The new arg is primarily for framework bindings that want to thread the React-tracked locale; `@comvi/react` ships `useFormatters()` for exactly this use case.

## Quick checklist

- [ ] React peer is `^18.0.0 || ^19.0.0`.
- [ ] No code calls `useI18nContext()` directly (or accept the deprecation warning; will be removed in v0.4).
- [ ] No `useEffect` deps relied on stable `t` / `tRaw` identity across locale flips (or the new identity-churn behavior is what you want).
- [ ] If you have many `<Link>`-like or other locale-only consumers, consider migrating from `useI18n()` to `useLocale()` for measurable re-render reduction (not required — `useI18n()` still works).

If you hit anything that isn't covered here, open an issue with `version: v0.3 migration` so we can extend this guide.
